02 / SECTION

1. 背景与问题

1.1 已确认事实

  • 公司分为自营部门和生态部门。自营通过闪回成交，生态通过买家成交，目前两个部门各自生成订单标签，存在名称和口径混乱。
  • 新订单初始标签只有“自营”和“生态”两个值。非买家中标订单初始为自营，买家中标订单初始为生态。
  • 部门扭转与货物实物流转无关，由成交渠道、机器人、手机号、买家售后退货和买家售前取消等业务节点触发。
  • 每条触发配置关联一个目标标签。订单成交时写入初始标签，首次命中跨部门触发后更新一次并冻结，后续不再更新。
  • 指定渠道规则优先级最高，不区分中标方。机器人规则和手机号规则均按中标方匹配，业务上二者互斥，不设置两者之间的优先级。
  • 系统只更新订单标签，不建设报表、看板、部门汇总或历史月报重分类；各部门按统一标签字段自行取数。

1.2 需要解决的问题

同一笔回收订单在成交后发生渠道、机器人、手机号、售后退货或买家取消时，自营与生态如何依据同一套可配置规则得到唯一、可追溯且最多变化一次的归属标签？

这个问题的核心是标签口径和更新边界。方案不回答货物当前由哪个部门实际持有，也不负责在系统中重算部门报表。

03 / SECTION

2. 目标、取舍与成功条件

2.1 本期目标

  1. 新成交订单能按统一依据生成唯一的自营或生态初始标签。
  2. 命中五类触发条件时，系统能依据配置的目标标签完成至多一次跨部门标签更新，并冻结结果。
  3. 每次标签变化都能追溯到中标事实、触发对象、规则版本、业务事件和生效时间。
  4. 系统输出一致的订单标签字段，供各部门自行取数。

2.2 方案取舍

全部线下人工改标无需事件接入无统一时点、难审计、易反复修改不推荐

同时建设报表、重算和资金拆分看似完整超出本期边界，放大口径和结算风险本期不做

4. 本期范围与明确不做

4.1 P0 范围

  1. 成交生成初始标签
  • 非买家中标写自营，买家中标写生态。
  • 中标方缺失时不猜测，进入待归因。
  1. 五类触发规则配置
  • 指定渠道成交。
  • 指定机器人中标。
  • 指定手机号中标。
  • 买家售后退货完成。
  • 买家售前取消并转闪回成交。
  • 每类规则配置一个目标标签，以及稳定匹配对象、业务节点和生效状态。
  1. 首次跨部门更新与冻结
  • 当前标签与目标标签不同时更新一次并冻结。
  • 目标相同时只留痕，不冻结。
  • 冻结后继续记录事件，但拒绝自动再次更新。
  1. 规则与订单标签追溯
  • 规则列表可查询配置、操作人和操作时间。
  • 订单标签详情可查看初始标签、当前标签、触发事件、规则版本、处理时间和冻结状态。
  1. 统一标签字段输出
  • 自营、生态按同一字段取数。
  • 系统不生成部门统计报表。

4.2 本期不做

  • 不建设部门订单报表、统计看板、月报重分类或自动对账。
  • 不处理分成、结算和资金拆分。
  • 不把部门扭转解释为货物实物流转。
  • 不允许一个订单同时存在多个当前归属标签。
  • 不允许冻结后由后续业务事件自动反转。
  • 不允许运营直接修改订单标签。
  • 不自动回填或重算全部历史订单。
  • 不按渠道名称、手机号或机器人名称猜测目标标签。
  • 不在目标标签含义尚未确认时扩展出“企业购”等独立归属值。
  • 首期不承诺原型之外的复杂规则发布、定时生效或批量剔除能力。

5. 核心业务规则

5.1 初始标签

中标事实初始标签当前标签初始值状态
非买家中标自营自营未扭转
买家中标生态生态未扭转
中标方缺失无无待初始归因

处理规则：

  • 初始标签在订单成交时写入。
  • 初始标签一经生成不可由业务事件修改。
  • 标签写入失败不回滚成交主流程，进入标签处理重试队列。
  • 中标方缺失时不默认归为任一部门。

5.2 五类触发条件

触发类型匹配依据业务节点标签处理
指定渠道成交渠道 ID渠道成交订单生成后不判断中标方，按规则目标标签处理；优先于机器人和手机号规则
指定机器人成交机器人 ID，且该机器人中标机器人中标时按规则目标标签处理
指定手机号成交手机号稳定标识，且该手机号中标手机号中标时按规则目标标签处理
买家售后退货受控售后事件 ID、订单和退货完成结果售后退货审核通过并完成退货标签保持生态；若当前不是生态则记录异常待核查
买家售前取消受控取消事件 ID、订单、付款状态和转闪回结果已付款且买家取消转闪回成交后标签保持生态；若当前不是生态则记录异常待核查

补充约束：

  • 渠道、机器人和手机号规则可在同一配置中关联自营或生态目标标签，但方向由订单当前标签与目标标签共同决定。
  • 机器人 ID 和手机号均基于订单实际中标方匹配，不能用成交渠道反推中标方。
  • 手机号使用稳定标识和脱敏展示，不在列表、日志中展示完整号码。
  • 售后退货与售前取消属于标签保护型事件，不应把已归生态的订单自动改成自营。

5.3 扭转方向与冻结

当前标签配置目标标签结果是否冻结
自营生态更新为生态，方向为“自营转生态”是
生态自营更新为自营，方向为“生态转自营”是
自营自营命中但无需扭转否
生态生态命中但无需扭转否

冻结后的行为：

  • 渠道、机器人、手机号和售后事件仍进入事件流水。
  • 流水结果标记为“已冻结，不更新”。
  • 不允许后续事件覆盖当前标签。
  • 晚到事件不覆盖既有更新；若业务时间早于首次更新，进入核查。
  • 异常修复必须走独立审批并形成新的修复记录。

5.4 多规则命中与优先级

  1. 渠道规则最高优先级，强制执行，不区分中标方。
  2. 渠道与机器人或手机号同时命中时，渠道规则胜出。
  3. 机器人和手机号之间不配置优先级。
  4. 正常情况下同一订单只有一个成交方，不会同时命中机器人规则和手机号规则。
  5. 数据异常导致机器人和手机号命中不同目标标签时，停止自动更新并进入冲突队列。
  6. 同一生效期内，同一个具体渠道、机器人或手机号只允许存在一个目标标签；重复配置在发布时阻断。
  7. 多个事件按业务生效时间判断先后，以首个导致跨部门更新的有效事件为准。
flowchart TD
    A[收到触发事件] --> B{标签已冻结?}
    B -- 是 --> C[记录事件，不更新]
    B -- 否 --> D{渠道规则命中?}
    D -- 是 --> E[采用渠道目标标签]
    D -- 否 --> F{机器人或手机号命中?}
    F -- 唯一 --> G[采用命中目标标签]
    F -- 冲突 --> H[进入冲突队列]
    G --> I{当前标签等于目标标签?}
    E --> I
    I -- 是 --> J[记录无需扭转]
    I -- 否 --> K[更新一次并冻结]

6.2 归属规则列表

字段：

  • 规则名称。
  • 最终归属部门：自营/生态。
  • 触发条件：渠道、机器人、手机号、买家售后退货、买家售前取消。
  • 触发值摘要：渠道名称、机器人名称、脱敏手机号、事件条件。
  • 关联回收类型。
  • 状态：草稿、待审核、生效中、已停用。
  • 操作人、操作时间、版本。

操作：

  • 查询。
  • 配置订单归属。
  • 编辑草稿。
  • 查看日志。
  • 导出当前筛选结果。

交互约束：

  • 仅“生效中”的规则参与事件匹配。
  • 编辑生效中规则必须生成新版本，不能原地覆盖历史版本。
  • 无权限用户只能查看或不能进入配置页。
  • 导出只包含规则配置，不包含完整手机号。

6.3 新建/编辑归属规则

通用字段：

字段要求
所属部门草稿的提交方；不能替代目标标签
触发条件五类受控枚举
触发值根据条件展示渠道、机器人、手机号或业务事件配置
关联回收类型可多选或按现有系统参数选择，最终是否必填待确认
归属部门/目标标签自营或生态
生效时间必填；是否支持定时生效待确认
备注记录配置原因

动态字段：

触发条件动态字段
按渠道选择渠道，支持多选；显示渠道 ID
按机器人选择机器人名称，支持多选；保存机器人 ID
按手机号录入手机号，支持多个英文逗号分隔；保存稳定标识，页面脱敏

保存校验：

  • 必须选择一个触发条件和一个目标标签。
  • 根据条件至少填写一个有效匹配对象。
  • 同一规则内不能配置多个目标标签。
  • 同一对象在同一生效期内不能冲突。
  • 手机号格式、数量和脱敏规则校验通过。
  • 目标标签枚举与基础标签定义一致。
  • 规则必须记录提交人、审核人和版本。

6.4 订单标签详情

展示：

  • 订单号。
  • 中标方。
  • 初始标签及生成时间。
  • 当前标签。
  • 标签状态：待初始归因、未扭转、已扭转冻结、冲突待处理、异常待修复。
  • 首次跨部门更新事件。
  • 规则 ID、规则版本和关联回收类型。
  • 事件业务时间、系统处理时间和事件来源。
  • 后续命中但因冻结未更新的记录。

页面只读，不允许直接编辑标签。

6.5 待归因与冲突

首期按原因分类：

  • 中标方缺失。
  • 渠道与对象规则数据异常冲突。
  • 机器人与手机号异常冲突。
  • 重复事件或晚到事件。
  • 事件来源字段缺失。
  • 标签写入失败。
  • 售后保护事件与当前标签不一致。

每条记录应显示订单、原因、首次发生时间、最近发生时间、影响标签和责任人。首期不提供无审批批量改标签。

9. 异常、恢复与发布边界

场景处理用户可见结果
中标方缺失不猜标签，进入待归因显示待初始归因
标签服务失败不回滚成交，异步重试显示处理失败及重试状态
重复事件按幂等键去重只保留一条有效处理
命中但目标相同记录事件显示无需扭转
已冻结后再次触发只记录事件显示已冻结，不更新
渠道与对象规则冲突以渠道为准展示被覆盖的规则记录
机器人与手机号异常冲突不自动更新进入冲突队列
晚到事件早于首次更新不覆盖当前标签进入核查
售后事件对应订单不是生态保持事件记录进入异常待核查
规则对象不存在不模糊匹配提示配置对象无效
历史订单无新字段不自动回填标记历史未归因

发布建议：

  1. 先接入事件并影子计算标签，不改正式订单标签。
  2. 按自营、生态分别对账初始标签和扭转结果。
  3. 小范围启用首次更新和冻结。
  4. 确认无重复更新、取数一致和事件追溯完整后扩大范围。
  5. 出现冻结后被二次更新、大面积冲突或不一致取数时停止扩大并回退到影子模式。

12. Gate 状态、G2 评审判断与下一步

12.1 当前判断

建议保留“成交初始化 → 五类事件配置 → 首次跨部门更新 → 冻结 → 统一下游取数”的最小范围。原型已经覆盖主要业务来源和配置页雏形，可以进入 G2 逐项评审；原型中的扩展条件和优先级说明不能直接研发落地。

12.2 需要优先关闭的决定

  1. Q-012：保值换新、企业购是否属于本期；若属于，它们与五类条件的位置如何调整。
  2. Q-013：五类触发对应哪些正式业务事件和生效字段。
  3. Q-014：售后退货和售前取消的完成条件如何由系统稳定判断。

12.3 评审后动作

  • 以本文件为 G2 方案基线，业务评审确认主流程、状态、页面字段、优先级和异常处理。
  • 修订 Axure：修正“企业够”、移除与本期不一致的优先级说明，补状态、冲突、冻结、无权限和失败交互。
  • 业务评审通过后登记 G2，再进入规格与测试；当前不生成最终 spec、正式测试或研发执行结论。
